## 1. 프로젝트 배경 및 목적

### 1.1 배경
고령화 및 1인 고령 가구 증가에 따라, 노인의 일상생활(복약 관리, 실내 이동 보조, 정서 대화)과 주거 안전(낙상 감지, **가스불 미차단 등 주거 화재·안전 사고 예방**)을 통합 지원하는 생활 밀착형 돌봄 수요가 증가하고 있다.

### 1.2 목적
본 프로젝트는 **AI 컴패니언 로봇**(이동형 바퀴 로봇 + 충전 스테이션 겸 종합 설정 터치스크린 키오스크 콘셉트)을 중심으로, 기존 1~4단계 프로토타입을 4대 확장 모듈로 발전시키는 소프트웨어 플랫폼을 구축한다.

* **소프트웨어공학 학습 및 실무 관점 통합**: 단순 기능 구현을 넘어 비즈니스 목표, 수익성(렌탈 단가 및 AI 추론 비용 절감), 외부 연동 구조, 요구사항 추적성을 종합적으로 설계·검증한다.
* **가상 시뮬레이션 기반 검증**: 실물 하드웨어 제작 없이 가상 시나리오 입력(Input)과 그에 상응하는 출력(Output)을 통해 소프트웨어 동작과 안전 시나리오를 검증한다.
* **본 v0.2 문서의 중점 범위**: 3번 개발자가 담당하는 **Smart Home Control(가스불 차단기 상태 확인·제어 및 어댑터 연동 구조)**을 중심으로 비즈니스 요구사항을 구체화하며, 추가 기능(복약 리마인더 고도화 등)은 Jira 워크스페이스 백로그 확인 후 점진적으로 보완한다.

## 4. 프로젝트 범위 (Scope)

### 4.1 포함 범위 (In-Scope)
* 기존 `companion_robot.py`의 1~4단계 코어 기능 및 기존 단위 테스트(`test_companion_robot.py` 8개 케이스) 100% 유지.
* **Smart Home Control 모듈 (현 단계 단일 대상: 가스불 차단기)**:
  * 명칭은 `Smart Home Control`이나, 현 단계에서는 **가스불 차단기(가스밸브)** 상태 확인 및 차단 시뮬레이션에만 집중한다.
  * UML `<<interface>> 스마트기기`, `가스밸브`, `스마트홈제어기` 기반의 독립 패키지(`smart_home/`) 설계 및 구현.
  * IoT 방식 기반 가스밸브 상태 조회(열림/잠김/차단중/오류/오프라인) 및 차단 제어 시뮬레이션.
  * 가스밸브 제어용 추상 어댑터 인터페이스 및 로컬 Mock 시뮬레이터 구현(다중 상용 스마트홈 플랫폼 비교/연동 논의는 현 단계에서 생략).
  * 기존 로봇 대화 의도 분류(`IntentClassifier`), 알림 기록(`AlertService`), 상태 영속화(`companion_state.json`), Tkinter GUI 탭 연동.
* **팀 공통 연동 규약 (`MODULE_INTEGRATION_GUIDE.md`)**: 4개 확장 모듈 및 추가 기능(예: 복약 리마인더 고도화 등) 개발 시 충돌 방지 기준 제공.
* **문서화 완료 · 타 팀원 구현 대상**: 복약 리마인더(Medication Reminder) 고도화 요구사항(`BR-07`, `PRD.md` Section 3.2)을 프로젝트 전체 백로그 문서화 차원에서 우선 정의함. 일상 대화 챗봇(Ollama 오픈웨이트 모델 연동) 세부 백로그는 추후 Jira 워크스페이스 동기화 시 반영.

### 4.2 제외 범위 (Out-of-Scope)
* 실물 바퀴 로봇, 물리 키오스크 기기, 실물 IoT 가스밸브 하드웨어 제작 및 현장 설치.
* 실제 119·의료기관·통신사 SMS 등 외부 실세계 긴급 발신.
* 클라우드 DB 서버 구축 및 사용자 계정/인증(현재 프로토타입은 로컬 JSON 파일 저장 방식 유지).
* 현 단계에서의 다중 외부 스마트홈 플랫폼(SmartThings, Home Assistant 등) 직접 연동 및 가스밸브 외 가전(에어컨·TV·조명·도어락 등) 구현(인터페이스 확장 여지만 유지).

## 5. 제약사항, 가정 및 비즈니스 리스크

### 5.1 주요 가정, 기술 정책 및 제약사항
1. **시뮬레이션 원칙**: 모든 센서·통신·차단 동작은 가상 입력과 로컬 상태 전이로 동작하며, 외부 실물 장비에는 영향을 주지 않는다.
2. **외부 Python 패키지 및 라이선스 정책**: **상업적 사용이 가능한 오픈소스 라이선스**(MIT, Apache-2.0, BSD, PSF 등) 패키지는 필요 시 도입 가능하다. 단, 상업 배포 시 소스 공개 의무가 발생하는 강한 카피레프트(GPL/AGPL) 패키지는 지양하며, 오프라인 단위 테스트는 Mock 어댑터로 외부 네트워크/모델 서버 없이도 통과해야 한다.
3. **일상 대화 AI 모델 방향**: 챗봇은 일상 대화 수준을 목표로 **오픈웨이트(Ollama 오픈소스)** 모델 활용을 기본 가정으로 둔다(세부 모델명·연동 방식은 해당 기능 작업 및 Jira 확인 시 확정).

### 5.2 OCR 대비 IoT 방식 우선 채택 근거
* **사업 모델 정합성**: 소프트웨어 단독 확인(OCR)보다 **IoT 가스밸브 자동 차단기**를 렌탈 패키지(월 43,900원)에 포함하는 모델이 수익성과 원격 차단 실행력 측면에서 명확하다.
* **테스트 및 신뢰성**: 영상 인식 오탐 변수 없이 결정적 상태 머신(`OPEN` / `CLOSED` / `ERROR` / `OFFLINE`)으로 단위 테스트와 경계 조건 검증이 용이하다.

### 5.3 비즈니스·안전 리스크 및 완화 방안

| 리스크 | 영향도 | 완화 방안 |
| :--- | :--- | :--- |
| 가스 차단 명령 실패 또는 통신 단절 시 실제 사고 위험 | High | 통신 오류·오프라인 상태를 명시적으로 모델링하고, 실패 시 즉시 `AlertService` 경고 알림을 생성하는 Fail-Safe 설계 적용 |
| 4인 개발자 및 각 AI 에이전트 동시 수정으로 인한 Git 충돌 | High | `MODULE_INTEGRATION_GUIDE.md`에 패키지 소유권·JSON 네임스페이스·의도 접두사·GUI 탭 연결 규약 고정 |
| 상업화 시 외부 패키지/모델 라이선스 분쟁 가능성 | Medium | 상용 허용 OSS(MIT/Apache-2.0/BSD 등) 및 상업 이용 가능한 오픈웨이트 모델 사용 원칙 준수 |

## 6. 성공 지표 (KPI / 검증 기준)

1. **기능 검증률**: Smart Home Control 신규 단위 테스트 전 항목 통과 및 기존 `test_companion_robot.py` 8개 테스트 회귀 통과(100%).
2. **예외 안전성**: 어댑터 통신 오류/오프라인/미등록 기기/중복 차단 시나리오에서 프로그램 크래시 없이 안전 메시지 및 경고 로그 반환.
3. **설계 분리도**: Smart Home 도메인 로직이 Tkinter GUI 및 외부 어댑터 구체 구현으로부터 분리되어 GUI·네트워크 없이도 독립 테스트 가능.
4. **요구사항 추적성**: `BRD(BR-*)` → `PRD(FR-SH-*, UC-SH-*)` → `상세 설계(클래스/메서드)` → `테스트 케이스(TC-SH-*)` 간 추적표 유지.
